Access, limits and errors

Base address

Every path is relative to the deployed application's address on the App Store. That address is not recorded in the repository, so the examples use $PSIRENS. Set it once in your shell:

export PSIRENS=https://<app-url>

The team token

  • The 4 routes that change data read Authorization: Bearer <token> and compare it with the TEAM_TOKEN environment variable. A wrong or missing token returns 401 {"detail":"unauthorized"}.
  • Keep the token in an environment variable, never on the command line, because a command line lands in the shell history and in ps. The examples read $PSIRENS_TOKEN. Set it without echoing: read -rs PSIRENS_TOKEN; export PSIRENS_TOKEN.
  • The deployed application sets no TEAM_TOKEN (FACT, owner, 23 November 2026), so on the App Store the write routes are guarded by the platform sign-in alone, and a script needs a signed-in browser session: tools/backfill_pull.py --ask-cookie.
  • With TEAM_TOKEN unset the application runs in single-user local mode and the write routes are open. The application refuses to start if TEAM_TOKEN is set while ALLOWED_ORIGIN is unset or *.
  • Read routes do not check the token. INFERENCE: on the App Store, user sign-in is enforced in front of the application, which is why requests arrive carrying X-Auth-Request-Email. Not verified from inside this repository.

Rate limits

  • General: 120 requests per 60 seconds per client address, on /api/tracks, /api/events, /api/hrr, /api/conjunctions and /api/coplanar.
  • Strict: 6 requests per 60 seconds per client address, on /api/pull, /api/refresh and POST /api/manual-elset.
  • Over the limit returns 429 {"detail":"rate limited"}. /api/meta, /healthz, /readyz, the interface, static files and DELETE /api/manual-elset carry no limiter.
  • Only one refresh or pull runs at a time. A second one while the first is running returns 200 {"status":"busy"}, not an error.

Caching

/api/tracks and /api/events send an ETag. Send it back as If-None-Match and an unchanged picture returns 304 with no body. The tag covers the content and the filters, not the generation time, so a narrower request is never answered from a wider one.

Errors

Every error body is JSON with a detail string that states the cause, for example 400 {"detail":"rank 9 out of range 1-5"}. The interface shows that text rather than a generic failure.

Headers on every response

Content-Security-Policy (self only), X-Frame-Options: DENY, and Access-Control-Allow-Origin set to ALLOWED_ORIGIN when it is a real origin.

GET/api/tracksThe plotted belt: one track per object▶

The data behind the main plot. Each object's track is ONE provider's fixes in ONE data mode, chosen by the provider agreement check, with the consensus drift rate, the observed fit beside it as a cross-check, and every provider's own status. The interface calls this on load and on every refresh.

Query parameters

NameDefaultMeaning
viewcombinedreal (REAL only), sim (SIMULATED only) or combined (REAL, SIMULATED, TEST, EXERCISE). Anything else is 400 unknown view.
modesthe view's modesComma list overriding the view: REAL, SIMULATED, TEST, EXERCISE. An unknown value is 400.
ranksevery rankComma list of HRR ranks 1 to 5, e.g. 1,2,3. Out of range or non-numeric is 400, never silently ignored. The interface sends 1,2,3 on first paint.

Response

Top level: view, generated_at, classification_banner, bounds {lon_min, lon_max, inc_min, inc_max}, count, ranks, stale_after_hours, tracks[]. Each track carries:

FieldMeaning
object_id, nameCatalogue number and the HRR common name (never the number twice)
data_mode, origin, targetMode of the served stream, where it came from, and a manual set's stated target
classification_marking, classification_markings[]Every distinct marking on the served samples, verbatim; the single field is them joined with " | "
samples[]{epoch, sub_lon_deg, inclination_deg, raan_deg, p}. p indexes provenance. Only samples whose own mode is in the view are served.
provenance[]{source, data_mode, classification_marking} for each sample's p
source, head_sourceThe provider chosen for the track and the provider of the newest fix
providersProvider to {count, status, note, newest_epoch, lon_at_common_deg, elset_rate_deg_per_day, drift_deg_per_day, drift_residual_deg, drift_withheld}. Status is one of track, agrees, set aside, disputed, unverified, aged out, not used, excluded (untagged history stored before 1.7.4).
agreement{mode, status (agreed, single, disputed, unchecked), primary, samples_untagged, common_epoch, agree_deg, max_lag_hours, positions, set_aside, unverified, aged_out, consensus}
drift_deg_per_dayThe PUBLISHED rate: the median of the agreeing providers' element-set rates where there is one, else the observed fit. Positive is east.
drift_basiselement_sets or observed_fit: which of the two the published rate is
drift_consensus{rate_deg_per_day, min_deg_per_day, max_deg_per_day, providers, count, method}, or null
drift_observed_deg_per_day, drift_observed_withheld_reasonThe least-squares fit to the track provider's own fixes, and why it is null when it is
drift_residual_deg, drift_fit_hours, drift_fit_points, drift_fit_harmonicDescribe the OBSERVED fit only (rms residual, baseline, fix count, whether the daily libration was modelled). May be null beside a published consensus rate.
drift_crosscheck{difference_deg_per_day, agrees}: consensus against observed fit; disagrees beyond 0.05 deg/day
drift_withheld_reasonWhy there is no published rate, when there is none
drift_since_eventEpoch of the newest CONFIRMED E-W manoeuvre; the observed fit uses only fixes after it
ra_degRight ascension of the ascending node for the RA bearing needle
curl -s "$PSIRENS/api/tracks?view=real&ranks=1,2,3"
curl -s "$PSIRENS/api/tracks?view=real" | jq '.tracks[] | select(.object_id=="64467") | {name, drift_deg_per_day, drift_basis, agreement: .agreement.status}'
GET/api/eventsThe Shift Brief: what changed, newest first▶

Events detected on the resolved view, computed once per store change in the background and never per request. Filtered exactly as /api/tracks, so the brief never lists an object the plot is not showing.

Query parameters

view, modes and ranks, with the same meaning and validation as /api/tracks. Supports If-None-Match.

Event types

TypeMeaning
STARTED, STOPPED, EWEast-west manoeuvre: the drift rate either side of a 3-hour split differs beyond 0.02 deg/day and 6 standard errors
NSNorth-south manoeuvre: a median inclination step beyond 0.008 deg
LEAVINGEarly warning: the newest fixes depart from the track fitted over the 72 hours before. Always SUSPECTED.
QUIETNo fix for 12 hours from an object that usually reports at least every 4 hours, judged only while the belt is current

Tier is CONFIRMED or SUSPECTED. Evidence that peaks at the last testable split is never CONFIRMED.

Response

Top level: view, ranks, generated_at, reference_epoch, belt_current, lookback_hours, thresholds {ew_floor_deg_per_day, ns_floor_deg, sigma, quiet_hours, max_residual_deg}, compute_seconds, count, events[].

Each event: id, object_id, type, tier, epoch, detectable_from, data_mode, name, rank, country, the type's numbers (rate_before/rate_after, delta_inc_deg, age_hours, usual_cadence_hours) and an evidence block (series, split, the two fitted lines, method). No event carries a projected approach.

1.7.12 An east-west event's epoch is the fit crossing: where the trend fitted before the burn meets the one fitted after it. The evidence gains timed_by (fit crossing or 3-hour split) and crossing {epoch, sigma_hours, half_width_hours, coverage 0.95, method}, or null when the fits do not meet within 6 hours of the split, in which case the split stands. The half-width is 2.6 standard errors, measured to hold the true burn time 95 times in 100. The id is keyed on the epoch rounded to the nearest hour, so it holds as new data arrives. detectable_from is a day after the later of the crossing and the split.

curl -s "$PSIRENS/api/events?view=real&ranks=1,2,3" | jq '.events[] | {type, tier, name, epoch}'
GET/api/hrrThe JCO high-interest list▶

The dynamic JCO HRR GEO list, pulled from UDL every 6 hours (HRR_REFRESH_SECONDS) with a bundled snapshot as the fallback. The interface joins tracks to it and plots REAL objects on it only. It is the naming authority for every other route.

Response

marking, source, regime, generated, count, and objects: catalogue number to {name, country, rank, affiliation}. Affiliation is RED, BLUE, OTHER (a known country on neither list) or UNKNOWN (no country given), resolved from the AFFILIATION_RED and AFFILIATION_BLUE policy lists. It colours the RA needle and nothing else.

curl -s "$PSIRENS/api/hrr" | jq '.objects["43683"]'
GET/api/conjunctionsClosest-approach screen for one object▶

Propagates the target and every object within 10 degrees of longitude with SGP4 over the screening window (CONJ_WINDOW_HOURS, 168) and reports the closest approach. Computed on demand when an object is selected, from the same provider the plot uses. The interface's inspector calls this.

Query parameters

NameMeaning
target (required)Catalogue number. Absent is 400 {"detail":"target required"}. An unknown or unusable target returns 200 with target: null and a detail naming why.

Response

  • target: {id, name, tle, tle_provenance}. tle is the provider's own two lines, or null when none was issued.
  • tle_provenance: {source, source_class, epoch, native, classification_marking, rev_no, ephem_type, data_mode, propagation_refused, copyable, copy_denied_reason, tle_withheld_reason}. The copy control is offered only for a plain unclassified, caveat-free marking.
  • neighbours[]: {id, name, sub_lon_deg, range_now_km, min_km, tca, tle, tle_provenance}, nearest first.
  • not_screened: nearby objects whose element set could not be propagated without an assumption (no stated SGP4 type, no B*, or none at all).
  • window_hours, computed_at.
curl -s "$PSIRENS/api/conjunctions?target=64467" | jq '.neighbours[:5][] | {name, min_km, tca}'
GET/api/coplanarCo-Planar chart data for one object's neighbourhood▶

Coplanar angle (the mutual inclination of two orbital planes) against absolute longitude difference, for every object within COPLANAR_HALF_WIDTH_DEG (20) of the primary, with a history trail. Small angle and small separation is the co-orbital geometry to watch. Computed on demand when the Co-Planar view opens.

Query parameters

target (required): catalogue number. Absent is 400. An unknown primary returns 200 with primary: null and a detail.

Response

  • primary: {id, name, inclination_deg, raan_deg, sub_lon_deg}.
  • tracks[]: {id, name, group, points[]}. Each point is {coplanar_deg, lon_diff_deg, epoch}, oldest first. The LAST point comes from the element set; earlier points pair stored samples that both carry RAAN within 6 hours of each other (COPLANAR_PAIR_HOURS). Capped at 60 points (COPLANAR_MAX_POINTS). One point means no usable history, not an error.
  • half_width_deg, computed_at.
curl -s "$PSIRENS/api/coplanar?target=43683" | jq '.tracks[] | {name, latest: .points[-1]}'
GET/api/metaRunning version, configuration and ingest health▶

The first place to look when anything seems wrong. Names the running build and says, in counts and one plain line, what the last ingest cycle actually did.

Response

FieldMeaning
versionThe running build, read from the application itself
classification_default, viewsDefault marking, and the data modes each view shows
refresh_seconds, refresh_lookback_hours, retention_daysRefresh cadence (3600), how far each scheduled refresh looks back (24) and how long fixes are kept (90)
manual_countActive operator element sets
last_refreshLast tick. Advances whether or not a record arrived: never read it alone.
last_successful_ingestLast cycle that merged at least one new fix
newest_sample_epoch, data_age_hours, stale, stale_after_hoursHow old the freshest fix is, and whether that passes the 24-hour alarm
last_ingest_addedNew fixes merged in the last cycle
last_ingest_requests, last_ingest_request_failuresUpstream requests made and how many failed
last_ingest_errors[]Failure reasons, e.g. HTTP 401 (credentials), HTTP 403 (entitlement)
last_ingest_rowsRaw records returned by UDL, INCLUDING responses that were set aside and asked for again in halves
last_ingest_fetched, last_ingest_kept, hrr_list_sizeDistinct objects offered, how many survived the mode and HRR filters, and the list size
last_ingest_rejected, last_ingest_rejected_reasonsRecords refused at the boundary and why: no catalogue number, no usable epoch with a time zone, incomplete elements, no provider (source), no classification marking, no recognised data mode. Never filled in.
last_ingest_requests_halved 1.7.9Responses at or above the 9000-row threshold that were set aside and re-requested as two halves
last_ingest_truncated_windows 1.7.9Windows still at the threshold at the smallest slice. Above 0 means newer fixes may be missing.
store 1.7.13The ledger store: backend ("ledger"), version (changes with every change to the held store), snapshot_seq, snapshot_age_hours, segments_since_snapshot, last_write_bytes (an hourly refresh is of the order of 1 MB, never the whole store), boot_seconds and compact_hours (24). Health is answered from counters, so this route and /readyz no longer read the store file.

From 1.7.9 a healthy cycle reads healthy: 1177 new fix(es) merged for 581 high-interest object(s). Build 1.7.8 says "no new epochs in the window" even when fixes arrived: that line is wrong on 1.7.8, the counts beside it are right.
curl -s "$PSIRENS/api/meta" | jq '{version, data_age_hours, stale, last_ingest_added, ingest_diagnosis, store}'
POST/api/pullPull a chosen window from UDL now▶

An operator-defined pull, and the route a backfill uses. REAL and combined pulls are filtered to the HRR list and pruned; SIM pulls skip both. A re-pull of a fix already held re-tags untagged history with its provider and fills missing fields, so it is how pre-1.7.4 history gains provenance.

NameDefaultMeaning
moderealreal, sim or combined
hours24Relative window ending now, clamped to 1 hour to 366 days
start, endnoneAbsolute window in ISO 8601, e.g. 2026-11-01T00:00:00Z. Both or neither; a time with no zone is read as UTC; at most 366 days; start before end. When given, hours is ignored.

Response: {"status":"ok","mode","start","end","added","errors","fetched"}, or {"status":"busy"} while another refresh or pull runs.

The pull runs inside the request. A long window is many upstream slices with pauses between them, and the platform ingress closes a long request before the server finishes. For anything over a few days use tools/backfill_pull.py, which chunks the window and prints the exact range to re-run for any chunk that fails.
curl -s -X POST -H "Authorization: Bearer $PSIRENS_TOKEN" "$PSIRENS/api/pull?mode=real&hours=72"
python3 tools/backfill_pull.py --base "$PSIRENS" --check
python3 tools/backfill_pull.py --base "$PSIRENS" --days 90
POST/api/refreshRun the scheduled refresh now▶

Runs one scheduled cycle immediately: re-pulls the HRR list (forced, ignoring its 6-hour cadence), then pulls the last REFRESH_LOOKBACK_HOURS (24) of REAL element sets. No parameters.

Response: {"status":"ok","added","errors","hrr_count","fetched","kept","rows","requests","request_failures"}, or {"status":"busy"}. The same counts then appear on /api/meta.

curl -s -X POST -H "Authorization: Bearer $PSIRENS_TOKEN" "$PSIRENS/api/refresh"
POST/api/manual-elsetAdd a temporary operator element set▶

Adds an operator-supplied element set as mean Keplerian elements, so no TLE has to be built by hand. It is merged straight away, its provider is always MANUAL, and it expires after ttl_hours. Nothing is defaulted: the marking, the data mode and B* must be stated.

JSON body

FieldRule

nameRequired, 1 to 120 characters
epochRequired, ISO 8601 WITH a time zone (e.g. trailing Z); a time with no zone is refused
inclination_deg0 to 180
eccentricity0 or more, below 1
raan_deg, argp_deg, mean_anomaly_deg0 to 360
mean_motion_rev_per_dayAbove 0, at most 20
bstarRequired
data_modeRequired: REAL, SIMULATED, TEST or EXERCISE
classification_markingRequired, not blank, at most 64 characters
sourceOptional note of where the numbers came from, at most 64 characters
targetOptional, at most 120 characters
ttl_hoursOptional, default 24, at most 8760 (one year)

Response: {"status":"added","object_id"}. A body that breaks a rule returns 422 naming the field.

DELETE/api/manual-elset/{object_id}Remove an operator element set▶

Removes the operator element set and drops the object from the store, so it leaves the plot at once. Returns {"status":"removed","object_id"}, or 404 when no such manual set exists.

curl -s -X DELETE -H "Authorization: Bearer $PSIRENS_TOKEN" "$PSIRENS/api/manual-elset/EX-1"
GET/healthzLiveness for the platform▶

Always 200 while the server is up: {"status":"ok","storage":"writable"|"degraded","detail"}. A read-only store is reported as degraded rather than failing, so the platform never restarts an otherwise healthy container.

curl -s "$PSIRENS/healthz"
GET/readyzReadiness for the platform, with staleness▶

{"status":"ready","data_stale"} plus the full ingest health block from /api/meta. Stays 200 when the data is stale, on purpose: stale data is not unreadiness, and a restart would fix no feed and lose the store.

curl -s "$PSIRENS/readyz" | jq '{data_stale, data_age_hours, ingest_diagnosis}'

GET/static/{name}Allowlisted files▶

{name} is looked up in a fixed allowlist, never used as a file path, so anything not listed returns 404. The list:

  • Operator Guide: guide.html, linked from the top right of the interface, and its 12 figures guide-overview.png, guide-top.png, guide-bar.png, guide-rail.png, guide-plot.png, guide-legend.png, guide-inspector.png, guide-coplanar.png, guide-country.png, guide-stale.png, guide-brief.png, guide-focus.png.
  • HRR snapshot: hrr-geo.json, the bundled GEO subset of the JCO list used until the live list loads.
  • Icons and install: icon-512.png, icon-192.png, favicon-32.png, apple-touch-icon.png, psirens-banner.png, manifest.webmanifest.
curl -s -o guide.html "$PSIRENS/static/guide.html"
GET/docs · /redoc · /openapi.jsonFastAPI's generated documentation▶

The framework adds these by default: an interactive Swagger page, a ReDoc page and the machine-readable OpenAPI schema. They describe the same 16 routes, but with fewer of the rules above, because most validation is in the handlers rather than in typed parameters.

FACT: they are enabled in the running application and carry no token. Kept on by the owner's decision, 23 November 2026. They are served without the application's security headers, because those are added by the application's own handlers.
